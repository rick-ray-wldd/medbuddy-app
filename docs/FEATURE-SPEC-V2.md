# MedBuddy 功能規格書 v2

> 給守豐:這份是**要做什麼**與**不可以做什麼**。實作方式你決定,但第 6 節的規則是硬的。
> 取代 `docs/LINE-UX-SPEC.md` 的選單部分;該文件的 §2、§3、§6 仍然有效。
> 版本:2026-07-29 · 對應 commit `4db93ad` 之後

## 0. 範圍

**固定一對:一位長輩、一位照顧者、兩個 LINE 帳號、一個 subject。**

多照顧者、多住民、機構情境**明確排除在這一版之外**。`demo-pair.ts` 已經把這件事寫成契約:兩個 `LINE_DEMO_*_USER_ID` 指定哪兩支手機,`canClaimDemoRole` 拒絕第三支。不要為了「以後可能要」而預留結構 —— 那些結構會在真的需要時被改掉,現在寫只是猜。

兩張選單各 **4 格**(原本照顧者 6 格,縮成 4 格)。

```
照顧者                          長輩
┌──────────┬──────────┐        ┌──────────┬──────────┐
│ 記一件事  │ 產生回診單 │        │ 我的藥    │ 產生回診單 │
├──────────┼──────────┤        ├──────────┼──────────┤
│ 紀錄用藥  │ 切換身分   │        │ 用藥提醒  │ 切換身分   │
└──────────┴──────────┘        └──────────┴──────────┘
```

**移除:** 照顧者的「他問了什麼」「照顧對象」「開啟網頁」;長輩的「這顆是什麼」「再唸一次」「找家人」。

## 1. 資料模型

### 1.1 連結長輩與照顧者的是 subject,不是彼此

```
             subject: subj-father
             （藥是誰的）
              ↑                ↑
        elder 綁定         caregiver 綁定
        （我就是他）        （我替他看）
```

兩個 `RoleBinding` 指向同一個 `subjectId`,關係就成立。**不需要第三張「A 照顧 B」的表。**

現有型別不需要改:

```ts
type RoleBinding = {
  channelUserId: string;   // LINE userId
  role: "elder" | "caregiver";
  subjectId: string;       // 兩人相同 → 這就是連結
  boundAt: string;
};
```

### 1.2 儲存層有一個已知缺陷,不要在它上面疊新東西

`BlobRoleStore` 用 Vercel Blob,而 **Blob 沒有 read-your-writes 保證**。2026-07-29 production 實際發生:寫入 4 秒後讀回舊值,導致角色判斷錯誤。細節與證據寫在 `src/lib/roles/stores.ts` 的註解裡,已加上 process 內快取把窗口收窄,但**沒有真正修好**。

**這一版的規則:新功能一律走 `RoleStore` / `LogStore` 介面,不要直接呼叫 `@vercel/blob`。** 換成 Postgres 時才會是改兩個檔案而不是改二十個。

## 2. 角色切換 —— 先修這個

### 2.1 現在的問題

`bindRole` 規定「elder 綁定是終局」,所以點了「我是長輩」之後**無法切回照顧者**,連 demo 都做不下去。

### 2.2 為什麼原本要這樣,以及為什麼現在可以放寬

原本的理由沒有錯:照顧者那一面裝著家人寫下的、**關於長輩本人**的觀察 ——「他最近比較常喝酒」「上禮拜血壓藥忘記吃」。他讀到會受傷,然後家人就再也拿不到誠實的回報。

但那條規則是在「**任何人都能宣稱任何角色**」的前提下寫的。`canClaimDemoRole` 出現之後,前提變了:**只有兩支被設定的手機能綁定,第三支直接被拒絕。** 守門的工作已經由 gate 完成,終局規則變成只是在擋自己人。

### 2.3 要做什麼

```
bindRole 的終局規則改為受環境變數控制:

  MEDBUDDY_ALLOW_ROLE_SWITCH=true   → 允許 elder → caregiver
  未設定 / false                    → 維持終局(現行行為)

demo 部署設 true。
```

**並且在 `bind.ts` 保留原本的論證。** 不要刪掉那段註解 —— 它記錄的是「為什麼真實產品該關掉這個開關」,而那件事沒有因為 demo 需要而變成假的。

**驗收:** 兩支手機都能在長輩 ↔ 照顧者之間來回切換,切換後 rich menu 立即跟著換。

## 3. 照顧者的四個功能

### 3.1 記一件事

**目的:** 照顧者不定時輸入長輩的生活資訊(哪天忘記吃藥、哪天晚上吃了止痛藥),系統整理成**醫師可以據以調整劑量的表格**。

**已完成的部分**(`src/lib/observations/`):自然語言 → Gemini 切分 → 五類標記 → 存進 log。**每一筆 note 必須逐字出現在照顧者原文中,否則丟棄** —— 這條檢查已經實作且有測試,不要動它。

**這一版要新增的:把觀察整理成 formed 表格。**

目前 `/summary/[subjectId]` 是一串平鋪的觀察。醫師在三分鐘的門診裡需要的是可掃視的結構:

| 欄位 | 內容 | 來源 |
| --- | --- | --- |
| 日期 | 觀察發生的日期 | `observedAt` |
| 類別 | 症狀 / 自行用藥 / 飲酒 / 漏服 / 其他 | `kind` |
| 家屬原話 | **逐字,不改寫** | `note` |
| 相關藥品 | 若該觀察提到的藥名能在 register 解析出來,列出;否則留白 | grounding |

**規則(這條最重要):**

> 表格是**結構**,不是**改寫**。「家屬原話」欄位永遠是照顧者打的字,一個字都不能動。
> 系統可以**排序、分組、標日期、對應藥品**,不可以**摘要、潤飾、統一單位、推論頻率**。

「相關藥品」欄若解析不到就留白,**不要猜**。留白對醫師是資訊(家屬提到某個他不認得的東西),猜錯是傷害。

**不要做的:** 不要產生「建議調整劑量為 X」之類的結論。系統呈現事實,醫師做判斷 —— 這是整個產品的界線,寫在 `docs/PRD.md` §3.2。

---

### 3.2 產生回診單

**目的:** 照顧者無法陪同就診時,長輩帶著 QR 去給醫師掃描。

**已完成:** HMAC 簽章的短效 token(`src/lib/summary/share-token.ts`,8 小時 TTL)、QR 產生、`/summary/s/[token]` 醫師端頁面、送圖片到長輩 LINE。

**這一版要改的:**

1. **兩個帳號同時收到。** 目前只送給長輩。改成長輩與照顧者都收到同一張 QR 圖片。
   - 長輩收到的是**圖片**,不是連結 —— 這條不可以破例(`LINE-ADAPTER-SPEC` §6.1)。他不會點,他是拿給醫師掃。
   - 照顧者收到圖片**加**連結都可以,他沒有這個限制。
2. **QR 指向的頁面要包含 3.1 的表格。** 目前的醫師頁面只有用藥清單,要加上觀察表格 —— 那才是「照顧者不在場時替他說話」的東西。

**時效:** 8 小時 TTL 維持不變。就診當天有效、隔天失效,是刻意的:一張永久有效的醫療摘要連結是資料外洩等著發生。

**驗收:** 照顧者按下 → 兩支手機在 10 秒內都收到 QR 圖片 → 用第三方裝置掃描 → 看到用藥清單 + 觀察表格 → 8 小時後同一個 QR 失效。

---

### 3.3 紀錄用藥(藥袋 OCR)

**目的:** 照顧者拍藥袋照片 → 辨識藥品 → 寫進長輩的「我的藥」。

**現況:** 契約寫在 `docs/MEDICATION-BAG-OCR-MIGRATION.md`(557 行),**未實作**。webhook 目前直接丟棄 `image` 訊息。

**要做的:**

```
照顧者傳圖片
  → webhook 正規化成 InboundMessage { kind: "image", ... }
  → 下載圖片 bytes（api-data 端點,與 audio 同路徑）
  → Claude OCR：抽出「藥品名稱、劑量、每日次數、飯前/飯後、天數」
  → ⚠️ 抽出來的名稱視為「使用者輸入的文字」,丟進既有的 resolver
  → buildVerdict → 存成一筆 RegimenSnapshot
  → 回覆照顧者：辨識到什麼、有幾項認不出來
```

**規則(這條最重要):**

> OCR 的輸出**沒有任何特權**。它就是文字,跟長輩自己打字進來的文字走完全相同的 grounding → rules → verdict 路徑。
>
> 絕對不可以因為「這是從藥袋上讀到的、看起來很正式」就跳過解析、直接當成已知藥品寫進紀錄。

理由:OCR 會看錯字。`5mg` 和 `50mg`、`理眠錠` 和 `新理眠錠` —— 後者這個案例在這個專案裡真的發生過(resolver 曾經把不存在的藥配對到一個真實的苯二氮平類許可證)。**認不出來要說認不出來**,`resolve.ts` 的三種 unresolved 類型就是為此存在。

**劑量時間要一起存下來**,因為 3.3 是 4.3 的資料來源。建議在 snapshot 的 item 上加:

```ts
type DosingSchedule = {
  timesPerDay: number;
  timing: "before_meal" | "after_meal" | "with_meal" | "bedtime" | "unknown";
  /** 藥袋上的原文,逐字。用於人工核對。 */
  rawText: string;
};
```

`unknown` 是合法值。藥袋上沒寫就是沒寫,不要填預設值。

**驗收:** 拍一張真實藥袋 → 認得出的藥出現在長輩「我的藥」 → 認不出的項目明確列為「認不出來」而不是消失 → 劑量時間存進 snapshot。

## 4. 長輩的四個功能

### 4.1 我的藥

**目的:** 看照顧者透過藥袋 OCR 建立的用藥紀錄。

**現況:** `lastCheckNarration()` 讀最近一筆 snapshot 重新敘述,已可運作。

**要補的一件事:時效邊界。** 現在它回傳最後一筆 snapshot,不管那是什麼時候拍的 —— 三個月前的紀錄會讀起來像今天早上。這是「看起來對的錯」。

```
若最近一筆 snapshot 超過 N 天（建議 30）：
  敘述前面加一句說明這是哪一天記錄的,而不是當成現況呈現。
```

**不要做的:** 不要因為紀錄舊了就不顯示。舊資訊加上「這是 X 月 X 日記錄的」是有用的;沉默不是。

---

### 4.2 產生回診單

與 3.2 同一個功能,長輩自己也能觸發。收到的一樣是**圖片**。

理由:照顧者可能忘了產生,而長輩人已經在診間。讓他自己能生成一張,是把控制權留給他 —— 而且他要做的事只是「舉起手機給醫師看」,不需要理解裡面是什麼。

---

### 4.3 用藥提醒時間

**目的:** 有結構地看到每天要吃什麼藥、飯前還飯後,並整理成友善的音檔,用 Serin 的聲音播放。

**資料來源:** 3.3 存下來的 `DosingSchedule`。**沒有 OCR 就沒有這個功能** —— 這是硬依賴,3.3 必須先完成。

**畫面結構:**

```
早上 飯後
  ・◯◯錠 1 顆
  ・△△膠囊 1 顆

中午 飯後
  ・◯◯錠 1 顆

晚上 睡前
  ・□□錠 1 顆

（有 2 項藥袋上沒有寫時間,列在最後,不猜）
```

**語音:友善、孫女的語氣,用 Serin 的聲紋。**

這裡有一條既有規則要遵守,而且它跟「孫女語氣」的關係需要講清楚 —— `LINE-UX-SPEC` §3:

> 不可使用疊字或「囉」「喔」 —— **一個把他當成正在衰退的產品,可能讓那件事成真。**

所以「孫女語氣」**不是**「阿公吃藥藥囉~」。溫暖來自:

| 溫暖從哪裡來 | 溫暖**不**從哪裡來 |
| --- | --- |
| Serin 真實的聲音、語速、停頓 | 疊字 |
| 短句、日常詞彙(「飯後」不是「餐後」) | 語尾助詞 |
| 稱謂自然(「爸」而不是「使用者」) | 表情符號 |
| 唸完不催促、不問他吃了沒 | 「要記得喔」這類提醒式責備 |

**文字產生方式:** 從 `DosingSchedule` **確定性**組出來的固定模板,不是 LLM 寫的。理由與現有的 narration 相同 —— 這段話會被一個人照著吃藥,它的每一個字都必須可以追溯到藥袋上的資訊。

**語音產生方式:** 沿用既有機制 —— 文字 sha256 → 找 Blob 裡 `line-audio/pre-{hash}-{ms}.mp3` → 有就附加,沒有就純文字。這個雜湊索引保證**語音講的字和文字一模一樣**。時間表變了,雜湊就變,語音自動失效退回純文字 —— 那是正確的失敗方式。

**建議:** 藥袋 OCR 完成、時間表確定後,跑一次 `scripts/prerender-elder-speech.mts` 把該時間表的語音產生出來。或改成延遲快取(第一次被問到就合成並存起來)—— 設計已在對話中討論過,`prerendered-speech.ts` 的雜湊機制不需要改。

**不要做的:** 不要做「你吃了嗎」的確認、不要做連續天數、不要做未服藥警示。`LINE-UX-SPEC` §3 全部禁止,理由是被問「你吃藥了嗎」等於被要求認錯。

## 5. 交付順序

依賴關係決定順序,不要跳:

```
1. 角色切換                 ← 沒有它,後面每一項都很難測
2. 記一件事 → 表格           ← 只動呈現層,風險最低
3. 產生回診單 → 兩邊都收      ← 小改動,demo 價值高
4. 藥袋 OCR                 ← 最大的一塊,4.3 的前置
5. 用藥提醒時間              ← 依賴 4
6. 我的藥時效邊界            ← 幾行,隨時可插
```

第 4 項如果做不完,**5 就不要做**。一個讀不到資料的提醒功能比沒有這個按鈕糟 —— 而且按鈕是我們自己放上去的,按下去沒反應對長輩來說會讀成「我按錯了」。

**選單格子只放做得出來的功能。** 這是現在照顧者選單沒有「拍藥袋」的原因,也是這一版把兩張選單縮到 4 格的原因。

## 6. 不可違反的規則

這些不是風格偏好,每一條背後都有一個具體的失敗:

| 規則 | 若違反會發生什麼 |
| --- | --- |
| 臨床內容只能來自 `narrate(verdict)` | 系統會講出規則從未產生的醫療主張 |
| 照顧者的原話逐字保存,永不改寫 | 醫師讀到的是模型的話,不是家屬的話 |
| OCR 輸出必須走 grounding,不得直接採信 | 曾經配對出一個不存在的苯二氮平類藥品 |
| 認不出來就說認不出來,不猜 | 被猜錯一次的人不會再問第二次 |
| 長輩不收連結(圖片可以) | 他會點,而他是詐騙最鎖定的族群 |
| 不問他吃藥了沒、不做連續天數 | 羞恥會關掉這個溝通管道 |
| 不用疊字、不用「囉」「喔」 | 把他當成正在衰退,可能讓那件事成真 |
| 新資料一律走 `RoleStore` / `LogStore` 介面 | 換 DB 時會變成改二十個檔案而不是兩個 |
| 選單不放做不出來的按鈕 | 沉默會被讀成「我按錯了」 |

## 7. 環境變數

```bash
# 固定一對(demo 契約)
LINE_DEMO_ELDER_USER_ID=U...
LINE_DEMO_CAREGIVER_USER_ID=U...
LINE_DEMO_SUBJECT_ID=subj-father

# 角色切換(第 2 節)—— 真實部署應關閉
MEDBUDDY_ALLOW_ROLE_SWITCH=true

# 選單 id(由 scripts/register-rich-menus.mts 產生)
LINE_RICH_MENU_ELDER_ID=richmenu-...
LINE_RICH_MENU_CAREGIVER_ID=richmenu-...

# 既有
LINE_CHANNEL_ACCESS_TOKEN=
LINE_CHANNEL_SECRET=
BLOB_READ_WRITE_TOKEN=
GEMINI_API_KEY=
SUMMARY_SHARE_SECRET=
NEXT_PUBLIC_BASE_URL=

```

選單改版後要重跑 `npm run richmenu:render && npm run richmenu:register`,並把新的兩個 id 更新到環境變數 —— **舊的 id 會失效**。

## 8. 檢查工具

已經寫好的唯讀腳本,做這些功能時會一直用到:

```bash
npm run roles:ls                    # 誰綁成什麼角色
npm run roles:card -- <userId>      # 補送角色卡(demo 用)
npm run roles:unbind -- <userId>    # 解綁,同時解除 LINE 選單
npm run richmenu:ls                 # 頻道上有哪些選單
npm run speech:ls                   # Blob 裡有哪些預先產生的語音
node scripts/list-log.mts <subj>    # 某人的完整紀錄
```

`roles:unbind` 需要 `BLOB_READ_WRITE_TOKEN` **和** `LINE_CHANNEL_ACCESS_TOKEN` —— 綁定是兩個寫入(Blob 記錄 + LINE 選單),解綁也必須是兩個刪除。只做一半會讓伺服器與手機看到不同的事實。
